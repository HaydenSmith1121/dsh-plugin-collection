# 收录快照

**[← 回到首页](../README.md)** · **[收录规范（强制）](./收录规范.md)**

> 本文原在市场仓库 `dsh-plugins` 的 `collection/README.md` 下，描述的是当时的
> `collection/snapshots/` 目录。市场与插件分离之后，快照跟着插件搬到了本仓库，
> 路径变成 `snapshots/<插件>/<插件版本>/`。文中指向市场仓库文件的链接已改为绝对地址。

本仓库固定保存**经过验证的插件 tarball**，以及它们的来源信息。

它的存在只为一件事：**上游更新之后，当时验证过的那一版仍然装得回来。**

---

<a name="not-latest"></a>

## ⚠️ 收录的不一定是最新版本

**这是设计意图，不是缺陷。**

本目录收录的是「**在真机上验证过、装得上、跑得起来**」的那一版，
**不是「上游的最新版」**。两者经常不是同一个版本，而且这是刻意的：

| | 收录原则 | 上游发布节奏 |
|---|---|---|
| 目标 | 验证过的字节可复现 | 持续发新版 |
| 关注点 | 装得上、不崩 | 加功能、改结构 |

上游发新版时，可能出现这些情况 —— 而它们正是快照要挡住的：

- 撤回旧版本（unpublish）→ 老用户**装不回来**
- 同一版本号重新发布不同内容 → 装到的**不是验证过的那一份**
- 收紧 `peerDependencies` → 原本可用的 dsh 版本**突然装不上**
- 改动包结构（挪走 `lib/`、去掉 `cordis.patch.yml`）→ 装上了但**界面里没有**

所以：**需要最新版时，先按 [`收录规范.md`](./收录规范.md#process) 真机验证，再新增一套版本与快照，不覆盖旧版。**

> 每个版本「是不是当前在用的那一版」记在 `manifest.json` 的
> `versions[].status`（`latest` / `superseded`）里，被取代的那一版还有
> `supersededBy` 与 `supersedesNote`（写清为什么换）。
> 这里**没有**「是否已追平上游最新版」这种字段 —— 那需要一个会天天过期的答案，
> 而本仓库承诺的是「验证过的字节」，不是「追平上游」。

<a name="third-party"></a>

### 第三方插件为什么不在这里

市场与插件分离时确定的策略是：**本仓库只分发自研插件，第三方插件不由任何仓库再分发字节。**

早先随市场仓库一起分发的 4 个第三方插件（`@dsh-market/plugin`、`dsh-workbuddy-connect`、
`dsh-connect-trae`、`dsh-receipt`）因此都**不再有本仓库或市场仓库托管的 tarball**。
它们仍可能出现在市场目录里 —— 但那一行必须是**能采到的干净上游规格**
（npm 包或 GitHub 仓库），采不到就不在目录里，而不是拿一份来源含糊的字节顶上。

> 想装某个第三方插件，请去它的**上游仓库**按上游的说明装。
> 本仓库不为它背书，也不替它保管字节。
> 已经装过的用户不受影响 —— 已装的插件在 profile 里，与本仓库无关。

<a name="verify"></a>

## 完整性校验

每个版本都有 `sha256`，记录在 [`manifest.json`](../manifest.json) 里，
它保证「装回来的和当初验证过的是同一个字节」。

```bash
# 重新生成清单并逐个核对 sha256
node scripts/build-manifest.mjs

# 只校验不写盘（CI 用）
node scripts/build-manifest.mjs --check
```

校验失败会明确报出**哪一项**不一致：`plugin.json` 的 `id` 与目录名不符 /
tarball 不存在 / `sha256` 与 `plugin.json` 记的对不上 / 快照与 tarball 字节不一致 /
一个可用版本都没有 / `manifest.json` 已过期。

CI（[`.github/workflows/verify.yml`](../.github/workflows/verify.yml)）每次 push 都跑这套校验，
**并额外核一条**：`plugins/<id>/` 下的 tarball 与 `snapshots/<id>/` 下那套必须**逐字节相同**。

<a name="layout"></a>

## 目录结构

```none
plugins/<id>/
├─ plugin.json                     # 人工维护的唯一事实来源
├─ README.md                       # 面向用户的安装 / 配置 / 卸载
└─ <dsh 版本>/<包名>-<版本>.tgz    # 用户下载与安装的那个文件

snapshots/<id>/
└─ <插件版本>/<包名>-<版本>.tgz    # 不可变快照，与上面逐字节相同

manifest.json                      # 派生清单（含 sha256），由脚本生成，禁止手写
```

> ★ **两个版本层的含义相反**：`plugins/` 下那一层是 **dsh 运行时版本**（答「该装哪一套」），
> `snapshots/` 下那一层是**插件版本**（答「当时收录的是哪一版」）。
> 前者会随 dsh 基线变化，后者是**永久坐标** —— 所以不能合并。

快照是**不可变**的：已收录的目录不得修改、覆盖或删除。上游发新版时**新增**一套目录。

> ★ 上表里 `dsh-opencode-go-plus` 有 0.2.1 与 0.3.0 两个版本，但 `snapshots/` 下只有 0.3.0 ——
> **这不是漏了**：0.2.1 是从市场仓库迁过来的历史版本，当时从未作为一次「收录」发布过，
> 留在 `plugins/` 下只为回滚，它的字节仍由 `manifest.json` 里的 `sha256` 钉住。
> 规则见 [`收录规范.md` § 2.2.1](./收录规范.md#no-snapshot)。

<a name="install"></a>

## 如何安装

**不需要手动挑 tarball。** 两条路等价，任选一条：

- **方式 A（推荐）**：装一次市场面板（引导插件 `dsh-plugins-market`，托管在市场仓库），
  之后在左侧「插件市场」面板里点「安装」—— 市场会自动读目录并跑装前兼容性闸门。
- **方式 B**：按首页[各插件安装方法](../README.md#plugins-install)里的命令下载 tarball、核对 sha256、
  `dsh plugin --profile web add <tarball>`。

两条路的完整对照见首页的[「两种装法」](../README.md#two-ways)一节。

<a name="add"></a>

## 如何新增收录

1. 阅读 **[`收录规范.md`](./收录规范.md)** —— 收录规则是**强制**的
2. 确认真实来源（版本 / 作者 / 上游仓库 / 许可，四项齐全）
3. 在隔离环境真机验证通过
4. 按规范登记，并运行 `node scripts/build-manifest.mjs`

没有把握的，先进 Issue 问 —— **不要凭印象填版本号或作者**。
