<a name="why"></a>

## 一、为什么是 `0.1.6-alpha.1`，而不是 npm 默认装的那个

dsh 在 npm 上有三条发行通道，**默认通道恰恰不是我们要的那个**：

| dist-tag | 版本 | 说明 |
|---|---|---|
| `latest` | `0.1.5-rc.1` | `npm i -g @deepseek-ai/dsh`（**不带版本**）装的就是这个 |
| `next` | `0.1.5-rc.2` | |
| **`alpha`** | **`0.1.6-alpha.1`** | ★ 本仓库插件要求的 |

版本不对的后果不是「某个插件不能用」，而是**整棵插件树加载失败、`dsh web` 完全起不来**：

```none
Error: dsh: plugin tree failed to load: failed to import loader entry opencode-go-plus
(dsh-opencode-go-plus): The requested module '@deepseek-ai/dsh-llm' does not provide
an export named 'IMAGE_OFFLOAD_REQUIRED_CODE'
```

<a name="rules"></a>

## 二、两条必须记住的规矩

### 1. 安装 dsh 必须显式带版本号

```bash
npm i -g @deepseek-ai/dsh@0.1.6-alpha.1
```

### 2. 永远不要跑不带版本的升级

`npm i -g @deepseek-ai/dsh` 会**静默降级**回 `0.1.5-rc.1`，插件立刻又炸，**且没有任何提示**。
升级后重跑一次隔离环境校验（脚本在市场仓库）：

```bash
node scripts/verify.mjs
```

<a name="matrix"></a>

## 三、本仓库 8 个插件的实测矩阵

照各包 `package.json` 的 `peerDependencies` 逐一实测。
**「要求的 `@deepseek-ai/*`」这一列是选 dsh 版本的唯一依据。**

| 插件 | 对 `@deepseek-ai/*` 的要求 | `0.1.5-rc.x` | `0.1.6-alpha.1` | 判定 |
|---|---|---|---|---|
| **`dsh-opencode-go-plus`** | **整套精确 pin `0.1.6-alpha.1`** | **✗** | **✓** | `critical` ← **基线由它决定** |
| `dsh-ark-plans` | `dsh-llm-pi-ai` / `dsh-credentials` / `dsh-client-ui-conversation` 精确 pin `0.1.6-alpha.1` | ✗ | ✓ | `warn` |
| `dsh-memory` | 仅 `cordis ^4.0.2`（宿主半零包导入） | ✓ | ✓ | `ok` |
| `dsh-excel-viewer` | 仅 `cordis ^4.0.2` / `react ^18.2.0` | ✓ | ✓ | `ok` |
| `dsh-session-cleanup` | 仅 `cordis ^4.0.2` / `react ^18.2.0` | ✓ | ✓ | `ok` |
| `dsh-usage-stats` | 仅 `cordis ^4.0.2` / `react ^18.2.0`（宿主半零包导入） | ✓ | ✓ | `ok` |
| `dsh-workbuddy-quota` | 仅 `cordis ^4.0.2` / `react ^18.2.0` | ✓ | ✓ | `ok` |

> 每个插件的 `peerVerdict` / `peerNote` 都写在它自己的
> [`plugins/<id>/plugin.json`](../plugins) 里，上面这张表只是汇总。

### 为什么 `dsh-opencode-go-plus` 决定基线

它**整套** `@deepseek-ai/*` 精确 pin 在 `0.1.6-alpha.1`（沿用基线、未做改动），
而 0.1.5-rc.x 内置的 `@deepseek-ai/dsh-llm` 缺 `IMAGE_OFFLOAD_REQUIRED_CODE` /
`offloadedImageText` / `projectOffloaded*` 这些具名导出 ——
ESM 的具名导入在**模块求值阶段**就失败，于是整棵树加载不起来，而不是某个功能不可用。

它也没有任何兼容 0.1.5 的发布版本（基线 `0.1.0` / `0.1.1` / `0.1.2` 全都要求 alpha），
所以**只能升 dsh，不能退插件**。

### 为什么另外几个的「精确 pin」只是警告

`dsh-ark-plans` 同样精确 pin 了 `0.1.6-alpha.1`，但它的宿主半 `lib/index.js`
**不 import 任何 dsh 包**（只用 `node:` 内置模块，连凭据都走 `ctx.get('credentials')` 取服务），
客户端半是 factory-form CJS bundle、react 走平台 seed 表。因此换 dsh 版本只会得到
pnpm 的 peer 警告，不存在「缺具名导出 → 整棵树加载失败」那条失败面 ——
真正的版本敏感性只剩它注入的 provider profile 与用到的那个 Slot。

`dsh-session-cleanup` / `dsh-workbuddy-quota` / `dsh-usage-stats` / `dsh-excel-viewer` 同理：
只约束 `cordis` 与 `react`，不对 dsh 运行时版本通道设 pin。

> **判定为 `warn` 不等于「可以随便换版本」**：上面每一条结论都是**在 0.1.6-alpha.1 上实测**出来的，
> 换了版本要重新实测，而不是照着这张表推断。

<a name="status"></a>

## 四、当前支持状态

| dsh 版本 | 状态 | 说明 |
|---|---|---|
| `0.1.6-alpha.1` | **支持（本仓库基线）** | 6 个插件全部实测加载正常 |
| `0.1.5-rc.x` | 不支持 | `dsh-opencode-go-plus` 与 `dsh-ark-plans` 起不来 |
| 其它版本 | 未适配 | 未实测，不承诺 |

### 遇到本仓库未适配的 dsh 版本怎么办

1. **先回到基线**：`npm i -g @deepseek-ai/dsh@0.1.6-alpha.1`
2. 想在新版本上跑，先照 [`docs/收录规范.md` § 第 2 步](./收录规范.md#process) 在隔离环境里实测一遍
3. 实测结论要写进该插件 `plugin.json` 的 `peerNote`，并同步更新本页 —— 只写在聊天记录里等于没写

> 市场面板在做安装前的环境体检时，用的也是这套结论：它读市场仓库的 `compatibility.json`，
> 版本不在矩阵里会**明确报「无法判断」并要求用户自行承担风险**，而不是猜一个答案。
