# 收录规范（Collection Specification）

> **规范性文档。** 本文件定义本仓库的**强制**收录规则。
> 与本文冲突的做法一律不予合入；确有必要例外时，必须在 PR 里写明理由并由维护者批准。
>
> **范围**：本仓库的 `plugins/<id>/`（人工维护的配置与 tarball）、`snapshots/`（不可变快照）、
> `manifest.json`（由脚本派生）。**不**约束市场仓库
> [`dsh-plugins`](https://github.com/HaydenSmith1121/dsh-plugins) —— 那边的目录格式与采集规范
> 见其 [`docs/插件清单与来源.md`](https://github.com/HaydenSmith1121/dsh-plugins/blob/main/docs/插件清单与来源.md)。
>
> 本文由市场仓库早期的 `collection/SPEC.md` 改写而来（市场与插件分离之前，快照曾放在市场仓库里）。
> 规则本身没变，变的是**位置**与**这份仓库自己维护什么**。

---

<a name="why"></a>

## 一、这份规范解决什么问题

用户装的是「**收录当时那一版**」的 tarball。上游一旦发布新版，会连带发生这些事：

| 上游发生的动作 | 对用户的后果 |
|---|---|
| 撤回旧版本（unpublish） | 老用户重装时装不回来 |
| 用同一版本号重新发布不同内容 | 装到的东西和当初验证过的不是同一份 |
| 收紧 `peerDependencies` | 原本可用的 dsh 版本突然装不上 |
| 改动包结构（挪 `lib/`、去掉 `cordis.patch.yml`） | 装上了但 GUI 里没有 |

这些都不是用户能预判的。**快照的存在，就是让「当时验证过的那一份」永久可复现**，
不再取决于上游此刻发布了什么。

因此本规范的第一原则是：

> ### ★ 收录的是「验证过的那个字节」，不是「上游的最新版」。

<a name="layout"></a>

## 二、目录结构（强制）

```none
plugins/<id>/
├─ plugin.json                     # ★ 人工维护的唯一事实来源：一个插件一个配置文件
├─ README.md                       # ★ 人工维护：面向用户的安装 / 配置 / 卸载说明
└─ <dsh 版本>/                     # 如 0.1.6-alpha.1 —— 这一层是 dsh 运行时版本
   └─ <包名>-<插件版本>.tgz        # 用户下载与安装的那个文件

snapshots/<id>/
└─ <插件版本>/                     # ★ 这一层是**插件版本**，与上面相反（见 2.1）
   └─ <包名>-<插件版本>.tgz        # 与 plugins/ 下同名文件逐字节相同

src/<id>/                          # 可选：该插件的源码（不是每个插件都有）
manifest.json                      # 派生：由 scripts/build-manifest.mjs 生成，禁止手写
scripts/build-manifest.mjs         # 派生 manifest 并核对全部字节
```

> **人工维护的只有两样：`plugin.json` 与该插件的 `README.md`。**
> `manifest.json` 一律由脚本从事实反推生成 —— 手写清单必然与事实脱节。

<a name="two-layers"></a>

### 2.1 两个版本层的含义**相反**，这是刻意的

| 目录 | 版本层 | 含义 | 变更频率 |
|---|---|---|---|
| `plugins/<id>/<dsh 版本>/` | dsh 运行时版本 | 这套包适配哪个 dsh | 换 dsh 基线时新增一层 |
| `snapshots/<id>/<插件版本>/` | **插件版本** | 收录的是哪个插件版本 | 每次发版新增一层 |

> `plugins/` 那一层答的是「该装哪一套」；`snapshots/` 那一层答的是「当时收录的是哪一版」。
> 前者的路径会随 dsh 基线变化，后者是**永久坐标** —— 所以不能合并。

<a name="immutable"></a>

### 2.2 不可变性（强制）

- **已收录的 `snapshots/<id>/<版本>/` 一律不得修改、覆盖或删除。**
- **已发布版本的 tarball 字节不得改写。** `plugin.json` 里记了 `sha256`，脚本会逐个核对；
  对不上会直接报错，提示「已发布的字节不能被改写」。
- ✅ 发新版 → **新增**一个版本目录与一套快照，旧的原样保留。

> 改快照等于把「装回来的还是当初那一份」这条保证作废 ——
> 而那条保证正是本仓库存在的理由。

<a name="no-snapshot"></a>

#### 例外：`versions[]` 里 `snapshot` 可以是 `null`

表示「这一版**没有**不可变快照」。出现这种条目的唯一情形是：

- 它是从市场仓库迁过来的**历史版本**，当时从未作为一次「收录」发布过
  （`status: superseded`、`verifiedAt: null`）；
- 留在 `versions[]` 与 `plugins/<id>/<dsh 版本>/` 下是为了**回滚**，不是因为它是收录版。

这种条目的字节**仍然是被钉住的** —— `sha256` 记在 `plugin.json` 里，CI 每次 push 都会
重新计算并核对，所以「装回来的还是当初那一份」这条保证并没有缺口，
只是没有第二份物理副本。

> **新收录的版本必须带快照。** `snapshot: null` 只用于解释历史，不是可以照抄的省事写法。
> 目前全仓库只有一条：`dsh-opencode-go-plus@0.2.1`。

<a name="naming"></a>

### 2.3 目录名与文件名（强制）

- **`<id>`** = 包名去掉 scope。`@dsh-market/plugin` → `dsh-market-plugin`
- **`plugin.json` 的 `id` 必须与目录名完全一致**（脚本会校验）
- **`<插件版本>`** = 包内 `package.json` 的 `version`，**原样照抄**，不做任何规范化
- **tarball 文件名** = `npm pack` 的默认产物名，scope 里的 `/` 换成 `-`

<a name="process"></a>

## 三、收录流程（强制）

### 第 1 步：确认真实来源

按可信度依次核实，**不要跳过第 2 条**：

1. 包内 `package.json` 的 `author` / `repository`
2. **包内 `README.md` / `LICENSE` / `NOTICE` 声明的上游**
3. npm 包页面：`npm view <包名> repository homepage author`
4. 都查不到 → 标注「**未注明**」，并在 `plugin.json` 的 `originNote` 里写明核实过哪些地方

**硬性要求**：以下四项信息**必须齐全**，缺一不予收录。

| 字段 | 要求 |
|---|---|
| 版本号 | 包内 `package.json` 的实际版本，禁止凭印象填 |
| 作者 | 查不到写「未注明」，**不要留空、不要猜** |
| 上游仓库 | 第三方必须有 URL；确实无法定位写「无法定位」并说明核实过程 |
| 许可 | 按 `package.json` 的 `license`；没有就写「未声明」 |

**许可准入**：只收录**明确允许再分发**的许可（MIT / Apache-2.0 / BSD 等）。
无许可声明或明确禁止再分发的，**不予收录** —— 本仓库是在**分发字节**，不是只给个链接。

> 本仓库目前只收录自研插件（`origin: self`），因此这一节的实际工作量集中在
> 「派生自哪个上游」这件事上 —— 例如 `dsh-opencode-go-plus` 派生自
> [`Duskriver/dsh-opencode-go`](https://github.com/Duskriver/dsh-opencode-go)，
> 必须写明派生关系与差异，不能让用户以为装的是上游原版。

### 第 2 步：真机验证

**静态探测替代不了这一步。** 这台机器上的插件要在**真实的 dsh 运行时**里装一次、起来一次。

```bash
# 隔离环境脚本在市场仓库里（本仓库不重复实现一套）
git clone https://github.com/HaydenSmith1121/dsh-plugins
cd dsh-plugins
node scripts/dev-env.mjs install <tarball 绝对路径>   # 装进 ~/.dsh-dev，绝不碰生产 profile
node scripts/dev-env.mjs web                          # 起在 3090 端口
node scripts/verify.mjs                               # 四步校验：版本 / 依赖层 / 装配层 / 真实启动
```

必须记录（当前记录在各 `plugin.json` 的 `peerNote` / `notes`，以及包内 `docs/verification.md`）：

- dsh / node / pnpm 版本
- tarball 路径与 sha256
- 启动输出里的关键行（有无 `plugin tree failed to load` / `does not provide an export`）
- peer 约束是否与本仓库基线（`0.1.6-alpha.1`）兼容
- 有无副作用（写全局配置、起后台进程、需要联网 / 登录 / API Key）

### 第 3 步：登记（缺一处即视为未完成）

#### ① 放 tarball

```bash
id=<插件 id>              # 包名去掉 scope，必须与目录名一致
ver=<插件版本>            # 包内 package.json 的 version
dshver=0.1.6-alpha.1      # dsh 运行时版本层
mkdir -p "plugins/$id/$dshver" "snapshots/$id/$ver"
cp "$tgz" "plugins/$id/$dshver/"
cp "$tgz" "snapshots/$id/$ver/"     # 两份必须逐字节相同，脚本会核对
```

#### ② 写 `plugins/<id>/plugin.json`

字段含义见下面第四节，**可照抄的完整示例**直接用现有的
[`plugins/dsh-memory/plugin.json`](../plugins/dsh-memory/plugin.json)（最简，一个版本）
或 [`plugins/dsh-ark-plans/plugin.json`](../plugins/dsh-ark-plans/plugin.json)（两个版本，含 supersede）。
最低要求：`id` / `package` / `title` / `summary` / `tags` / `author` / `license` /
`origin` / `versions[]`。`versions[]` 里这一条要写全
`version` / `dshVersion` / `tarball` / `snapshot` / `sha256` / `bytes` / `files` / `status` / `verifiedAt`。

> `sha256` 可以先留空 —— 跑一次生成脚本会算出实测值并报出差异，再回填。
> 但**回填的一定是实测值**，不是抄来的。

发新版时，除了**追加**一条，还要把上一条的 `status` 改成 `superseded` 并补上
`supersededBy` 与 `supersedesNote`（写清这一版改了什么、要不要紧），
再把 `latest` 那条同步到顶层字段。

#### ③ 写 `plugins/<id>/README.md`

面向用户，必须包含：**安装方法**（面板装与手动装两条路都要给）、**配置**（需要 Key 的写清去哪儿填）、
**卸载 / 回滚**、以及这一版的已知限制。

#### ④ 生成清单

```bash
node scripts/build-manifest.mjs
```

> `manifest.json` **由脚本从事实反推生成，禁止手写。**
> 脚本会读各 `plugin.json` + 各 tarball 的 `package.json` + 实际字节，
> 算出 sha256 并逐个核对（与 `plugin.json` 记的那份、与快照那一份都要对上）。
>
> 它同时是**市场侧采集脚本的唯一输入** —— 市场按 `manifest.json` 为每个插件生成
> `catalog/plugins/<slug>.json`。所以这里的字段就是市场看到的全部事实。

### 第 4 步：提交前自检

```bash
node scripts/build-manifest.mjs --check    # 必须通过：只校验，不写盘
```

CI（[`.github/workflows/verify.yml`](../.github/workflows/verify.yml)）在每次 push 上跑的就是它，
外加两条：每个插件必须有 `plugin.json` 与 `README.md`；tarball 与快照必须逐字节一致
且 sha256 与清单相符。

<a name="fields"></a>

## 四、强制字段清单

### `plugin.json`（人工维护）

| 字段 | 说明 |
|---|---|
| `id` | **必须与目录名一致**，脚本会校验 |
| `package` | npm 包名（可能带 scope） |
| `title` / `summary` / `tags` | 展示用；`summary` 会进市场目录，不要写成一句「一个插件」 |
| `author` / `license` / `repo` / `homepage` | 来源信息，见第 1 步 |
| `origin` / `originNote` | `self`（本仓库自研）或派生来源，必须写清关系 |
| `needsConfig` / `usageNeedsConfig` | 要不要填 Key / 要不要配置才能用 —— 市场的筛选用它 |
| `peerRuntimePin` / `peerVerdict` / `peerNote` | peer 约束与**实测**结论；`peerNote` 要写清「为什么这个 pin 不会导致加载失败」 |
| `coexistenceWarning` | 与别的插件冲突时写在这里（例：`dsh-opencode-go-plus` 与 `dsh-opencode-go` 不能共存） |
| `notes` | 实现要点与实测结论；这是给下一个维护者看的，宁细勿略 |
| `collectNote` | 收录这一版的理由 |
| `source` / `sourceNote` | 源码在本仓库的位置（没有源码就留空并说明） |
| `baselineDshVersion` | 收录时的 dsh 基线 |
| `versions[]` | 见 2.2 / [2.2.1](#no-snapshot) / 第 3 步 ② |

### `manifest.json`（脚本派生，此处列出以便核对）

| 字段 | 来源 |
|---|---|
| `schemaVersion` / `generatedAt` / `repo` / `runtime` | 脚本自动 |
| `counts.total` / `withSource` / `versions` | 从各 `plugin.json` 数出来 |
| `plugins[].sha256` / `bytes` | **实际字节计算** —— 快照完整性的唯一依据 |
| `plugins[].install` | 由脚本拼出的可照抄安装命令（**PowerShell 形态**；POSIX 等价写法见各插件 README。市场面板那边会自己按用户所在 shell 生成两套） |
| `plugins[].versions[]` | 每个版本的 tarball / 快照 / sha256 / 状态 |

> `generatedAt` **只在内容真的变了的时候才推进**，避免每次跑都产生一次无意义提交。
> `--check` 因此判的是「配置与清单是否一致」，而不是时间戳。

<a name="not-latest"></a>

## 五、对「收录的不一定是最新版本」的解释

这是本仓库的**设计意图**，不是缺陷，所以必须在面向用户的文档里说明白：

- **收录标准**是「在真机上验证过、装得上、跑得起来」，**不是「追平上游」**
- 上游最新版可能改了 peer 约束、改了包结构，**反而装不上**
- 旧快照的价值恰恰在于：等上游发新版之后，**这一版还能原样装回去**
- 需要最新版时：先按第 2 步真机验证，再**新增**一套版本与快照，**不覆盖旧版**

因此仓库根的 `README.md` **必须**显式写出这条声明，且不得只用小字脚注带过。

<a name="pr"></a>

## 六、PR 检查清单（强制）

提交前逐项确认：

- [ ] tarball 放在 `plugins/<id>/<dsh 版本>/<包名>-<版本>.tgz`，快照放在 `snapshots/<id>/<插件版本>/<包名>-<版本>.tgz`
- [ ] 目录名、文件名、`plugin.json` 的 `id` 三者一致（[2.3](#naming)）
- [ ] **未修改、未覆盖、未删除任何已收录的快照或已发布版本的 tarball**
- [ ] **版本号 / 作者 / 上游仓库 / 许可**四项信息齐全（查不到已如实标注）
- [ ] 许可明确允许再分发
- [ ] 已在隔离环境真机装过并启动成功，证据已记录
- [ ] `plugin.json` 的 `versions[]` 已追加，上一条的 `status` / `supersededBy` 已更新
- [ ] 顶层字段（`version` / `tarball` / `sha256` / `bytes`）已同步到最新的那一版
- [ ] 该插件的 `README.md` 已写清安装 / 配置 / 卸载
- [ ] `node scripts/build-manifest.mjs` 已重新运行
- [ ] `node scripts/build-manifest.mjs --check` 通过
- [ ] commit message 说明收录了什么、版本号、以及为什么收这一版

<a name="self-change"></a>

## 七、本规范自身的变更

修改本文件属于**规范变更**，需要：

1. 在 PR 描述里说明动机与实际踩到的坑
2. 同步检查仓库根 `README.md` 与 [`docs/收录快照说明.md`](./收录快照说明.md) 是否仍然准确
3. 若是收紧规则，检查存量插件是否需要补齐信息
4. 若改动了目录约定，同步检查市场仓库的采集脚本（`scripts/sync-catalog.mjs`）是否跟得上 ——
   它读的是本仓库的 `manifest.json`，字段变了它就要跟着改
